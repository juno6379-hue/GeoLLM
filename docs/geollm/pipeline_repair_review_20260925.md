# GeoLLM 샘플 파이프라인 진단·수정 검토

이 문서는 AI 검토이며 독립 human gold가 아니다. route 이름 일치, registry exact hit, COMPLETED 상태를 답변 정확도로 환산하지 않는다. 지명 조회는 공간 분석의 선행 작업이 될 수 있고, 침선 검색과 사고 분석은 연관 후보가 될 수 있다. 판정 기준은 **요청한 대상·시간·공간·산출물의 보존, 실제 도구의 입출력, 근거와 누락 작업**이다.

## 실제 관측 범위

- 실행 중인 웹의 `setupPresetPrompts()`에서 가져온 100개 질의를 `/api/v1/tasks/stream`에 전달했다. 원문·페이지 hash·task ID·전체 SSE 이벤트를 저장했다.
- 지도 범위는 `{}`로 통일했다. 브라우저 화면의 지도 문맥이나 클릭을 검증한 것으로 표현하지 않는다.
- 최초 관측: `outputs/web-sample-review/live-presets-v1/`. 29 COMPLETED, 63 BLOCKED, 5 NEEDS_CLARIFICATION, 3 관측 시간초과. 이 숫자는 의미 정확도가 아니다.
- 100개 Ollama 비교 원본: `outputs/pipeline-comparison/baseline-v1/`. qwen2.5:1.5b, 69개 기본 구조·원문 인용 검사 통과, 27개 인용 불일치, 4개 JSON 파싱 실패. 통과한 응답에도 잘못된 슬롯과 기능 설명이 있다.
- 위 최초 Ollama 실험은 **lexical broker 재생 후보**를 썼다. 실제 서비스의 pgvector 후보와 동일하다는 주장을 할 수 없다. `--live-candidates`를 추가해 보존한 서비스 후보를 그대로 평가하는 후속 실험을 구분했다. 후보별 입력·출력·설명과 규칙/Ollama/혼합 순위를 함께 저장하며 실행에는 사용하지 않는다.

## 확인한 원인과 수정

1. **문서 주제와 실행 의도 혼동**: 관련 고시 family가 있다는 이유로 AIS 집계·지도 표시를 문서 검색으로 완료했다. 의도 파싱과 실행 분기가 공유하는 산출물 기준을 추가하고 명시적 문서 조회는 유지했다.
2. **후보 순위와 실행 자격 혼동**: 부산항이라는 지명 후보가 1위이면 이미 검증된 통항량 도구가 candidate_only로 남았다. 요청 산출물에 맞는 기존 후보 route를 재선택하고 registry 검증을 다시 적용한다. 후보나 검증 결과를 새로 만들어 넣지 않는다. 실제 위치·기간·DB 검증은 실행 단계에서 별도로 한다.
3. **항만 원천 조회 지연의 전파**: 모든 항만 도형의 unary union이 5초 제한을 초과했다. 지명 대표점 생성에 필요 없는 union을 제거하고 partial index 조건을 맞췄다. 실제 같은 73개 항만 그룹 조회는 8.54초→0.13초였다. 정상 원천은 장애 원천과 분리하되, 같은 이름의 불량 행이나 해당 후보 원천 장애는 계속 차단한다. 항만 면을 사용하는 분석은 대표점으로 대체하지 않는다.
4. **기간 및 설명 하드코딩**: 최근 N개월을 과거 적재 기간으로 조용히 바꾸지 않는다. 현재 월 기준 월별 coverage를 출처마다 검증하고 부족하면 차단한다. 최신 적재 월은 사용자가 명시하거나 기간이 없는 경우의 공개된 기본값으로 구분한다. 일 단위 요청은 월 자료로 수행했다고 주장하지 않는다. 고정 V-PASS 우세 문구와 고정 최근 12개월 설명을 제거했다.
5. **S-101 용어 매핑 누락**: ‘정박지는 S-101에서 어떤 Feature야?’는 사전의 단일 후보와 catalogue를 결합해 `AnchorageArea`를 반환한다. 복수 feature 후보는 첫 항목으로 임의 확정하지 않는다. 실제 source_kind·term_id를 도구/데이터 바인딩에 기록한다.
6. **웹 전송 단계의 결과 소실**: SSE 축약이 비공간 결과의 Feature 코드와 진단 행, 근거를 버렸다. 도메인 결과 필드와 EvidenceBundle·실행 provenance를 보존한다. 문서 preview 제한은 유지한다.
7. **시스템 진단에 문서 답변**: 적재 기간은 실제 traffic 테이블에서 조회하고, pgvector 확인은 실제 저장 벡터의 cosine top-k를 실행한다. 후자는 DB 연산만 검증하므로 PARTIAL이며 새 질의 embedding 품질까지 정상이라고 주장하지 않는다. 후보 제거 이유는 검토할 원래 질의/작업 ID가 없으면 추가 입력을 요청한다.
8. **공간 layer와 traffic 혼동**: spatial registry에 정박지·일반항로·통항분리 경계선의 질의 별칭을 연결했다. 통항분리 경계선과 통항량은 구분한다. 요청하지 않은 3km 반경을 자동으로 넣지 않는다. 경계선을 구역 면이라고 표시하지 않는다.
9. **적재 완료의 과장**: document_chunks 관련 source 조회만으로 raw·표준화·serving 전체 적재를 완료했다고 표시하지 않는다. 문서 근거 조회는 PARTIAL 또는 근거 없는 경우 BLOCKED로 표시하고, 실행하지 않은 ingestion report 도구를 실행 계획에서 제거했다.
10. **불충분한 사고 질의의 시간초과**: 사고 대상과 조회 행동은 분류하되, 실제 조회 필터가 없으면 DB 조회와 LLM fallback 대신 필요한 해역/관할·유형·기간을 요청한다. 41/42번을 위한 임의 기간이나 위치를 추가하지 않는다.
11. **등록·임베딩 현황의 검증 범위**: resolver 목록은 실제 capability registry에서 읽으며 실행 가능 상태를 증명한 것으로 취급하지 않는다. embedding 현황은 metadata 원천 경로에 Dataset/이 기록된 실제 청크의 NULL/non-NULL 집계다. 미등록 파일과 경로가 없는 청크는 포함하지 못하므로 PARTIAL이다.
12. **진단 요청의 지도 fast path 선점**: resolver 목록을 '보여줘'라는 요청이 그래프 진단 노드에 도달하기 전에 장소 조회로 실행됐다. 공통 진단 판정을 fast path 자격 검사에도 적용했다. `contracts-v6.jsonl`의 12/13 실패를 보존하고 수정 후 `contracts-v7.jsonl`에서 13/13을 확인했다.

## 검증 및 한계

동일 서비스 후보 후속 실험(`outputs/pipeline-comparison/live-candidates-v2/`)은 21/28/31/32/43/46/79/82번 8개를 평가했다. 강화된 구조·인용 검사 5/8 통과, 3/8 인용 불일치. 규칙/Ollama/단순 혼합/온도 1 혼합/registry-context 혼합 순위를 저장했지만 calibration을 학습한 것은 아니다. 이 결과도 의미 정확도가 아니다.

- 21: STANDARD_RAG 선택은 관련되지만 radius=100, time=2023-01-01을 원문 없이 생성했다.
- 43: STANDARD_RAG 선택은 관련되지만 표준 버전 2.0을 radius로 입력했다.
- 79: PLACE_LOOKUP을 DB 점검 도구로 설명하고 radius=1000, time=now를 생성했다. 실행 계약과 불일치한다.
- 82: 대상 작업 정보가 없다는 이유로 ABSTAIN/clarification을 제안한 점은 적절하다. 그러나 반경·날짜 슬롯은 여전히 생성했다.
- 46: 제공된 후보만으로 symbol 매칭 근거를 충족하지 못한다며 ABSTAIN한 점은 유용하다. 역시 무근거 반경·시간 슬롯이 남는다.

따라서 모델의 후보 부족 감지는 활용 가능성을 보였으나, 현재 qwen2.5:1.5b의 구조 통과 응답을 의도·슬롯의 사실 권위로 사용할 근거는 없다. Ollama 런타임 전체의 한계나 다른 모델의 성능으로 일반화하지 않는다.

`scripts/check_pipeline_execution_contracts.py`의 실제 API 검사 9/9가 통과했다 (`outputs/web-sample-review/contracts-v4.jsonl`). 이는 해당 회귀 계약 통과이며 전체 정확도 100%가 아니다. 최신 적재 월을 명시한 부산항 AIS 질의는 2023-12, 교차 격자 6행, 합계 6,847,473을 실제 DB에서 반환했다. 이는 격자·월별 집계의 합이며 고유 선박 수나 현재 통항량이 아니다. snapshot과 실제 SQL 파라미터를 보존했다.

동일 후보 Ollama 평가와 서비스 샘플/계약 검사를 병행한 `contracts-v5.jsonl`에서는 6/9 통과했다. 정의 질의 관측 timeout 및 두 통항 질의의 PORT_SOURCE_UNAVAILABLE이 발생했다. 부하 중 실패를 모델 의미 오류나 정상 실행으로 재분류하지 않았다. 후보 조회·지명 사전 precheck·사고/문서 DB 조회의 동기 작업을 웹 이벤트 루프 밖으로 이동했다. 상시 shadow 도입 전 자원 격리·동시 요청 검증은 별도 P0/P1 승격 조건이다.

아직 완성됐다고 볼 수 없는 항목: 독립 human gold/holdout, 원천 전체 적재 lineage, portrayal 매칭의 완결된 근거, 복합 작업 전체 완료 검증, 사고·기상·수심을 결합한 위험 분석, 실제 LiDAR 엔진과 최신 외부 예측 원천. QLoRA나 Ollama 실행 권한 승격은 적용하지 않았다.

## 확장성 판단과 다음 작업

현재 결과로 'Ollama가 의도를 잘 분류한다'거나 '혼합 점수가 규칙보다 우수하다'고 결론 내릴 수 없다. 검증한 것은 특정 모델(qwen2.5:1.5b)·프롬프트·후보 계약이며, Ollama는 실행 환경이다. 후보 부족과 추가 확인의 필요성을 감지한 사례는 있지만, 무근거 슬롯 생성과 도구 기능 오해가 운영 사용의 걸림돌이다.

확장 방향은 새 intent마다 분기를 추가하는 것이 아니라 **요청 산출물→필요 작업→등록된 capability 조합→슬롯/근거 검증→실행 결과별 완료 판정**이다. 예를 들어 침선 검색은 위치 해소·공간 검색을 조합하고, 사고 이력을 요구한 경우에만 사건 자료 조회를 추가한다. 장소 조회와 공간 분석을 상호 배타적인 정답 라벨로 만들 필요가 없다. 현재 구현은 이 구조의 일부 계약과 진단을 보완한 단계이며 범용 작업 조합기는 완성되지 않았다.
