# 한국어 의도·슬롯 보강 및 Qwen3.5 shadow 평가 작업계획

작성일: 2026-09-25, 상태 갱신: 2026-09-26. 범위: GeoLLM 공통 질의 파이프라인. **S0 기준선 고정, S1/S2와 KG·도구 연결 구현, S3 완료 감사 구현, S4 대표 shadow 실험 수행. 전체 계획 완료는 아니다.** 상세 결과와 한계는 [구현·평가 보고서](korean_pipeline_implementation_20260926.md)를 따른다. 아래 계획 수립 당시 상태와 목표를 실제 완료 결과로 해석하지 않는다.

Kiwi/4B는 설치했다. 4B 대표 10개에서 원문 계약 실패와 timeout이 발생해 현 설정의 전체 확대/운영 채택을 보류했다. 모델은 실행을 바꾸지 않는다. 독립 human gold·calibration·holdout, 조건부 9B 및 QLoRA 조건은 미충족이다. S1의 전체 문맥·시간 해소, S2의 실제 부정 조건 실행, S3의 모든 복합 산출물 엔진은 잔여 구현이다.

사용자 지정 순서: 원문 구간·단위·부정 표현 검증과 Kiwi 보강 → Qwen3.5 4B 동일 후보 비교 → 자원이 허용하면 9B → 작업·슬롯·질문·과잉 실행·지연 평가 → 조건 충족 후 QLoRA 판단. 이 문서는 실행 순서와 완료 조건을 정의한다. 계획의 수치 목표는 기존 측정 성능이 아니다.

## 1. 왜 이 작업이 필요한가

현재 문제는 단일 intent의 이름만 잘못 고르는 문제가 아니다. 장소 조회가 공간 분석의 선행 작업일 수 있고, 침선과 사고가 연관 후보일 수 있다. 그러나 관련 후보를 고른 것만으로 사용자가 요구한 검색·집계·지도 표시를 완료한 것은 아니다.

| 관측한 문제 | 원인에 대한 판단 | 이번 개선 |
|---|---|---|
| Ollama가 12개월을 반경, 버전 2.0을 거리로 입력 | 숫자를 슬롯 유형·단위·문맥과 연결하지 못함 | 원문 구간과 물리 차원을 검증하고 별도 정규화 |
| 없는 반경·날짜 생성 | 생성값과 원문/대화/지도 근거를 분리하지 않음 | 슬롯별 출처와 근거를 요구하고 미확인은 null |
| '위치 없이 부근 사고'를 '없, 부근'으로 검색 | 부정·결핍 표현을 검색 엔티티로 취급 | 형태·부정 범위·필수 위치 부족을 함께 판정 |
| '보여줘'가 지도 이동 fast path를 선점 | 행동 표현만으로 실행 대상 확정 | 공통 요청 계약을 모든 진입 경로에서 검사 |
| portrayal·지도 객체 질문에 문서만 반환하고 완료 | 필수 산출물과 실제 실행 결과 연결 부족 | 작업별 요구·선행조건·증거·완료 상태 보존 |
| Ollama 평가와 API 병행 시 timeout | 모델/DB 작업의 자원 경쟁 가능성 | 순차 오프라인 실험 후 별도 동시 부하 검증 |

키워드별 intent 분기를 늘리는 대신, **대상·행동·제약·산출물과 등록된 capability의 조합**을 공통 계약으로 표현한다. Kiwi는 형태 정보, LLM은 후보 해석, registry/KG는 기능·근거 검증, PostGIS와 도구는 실제 결과를 담당한다. 어떤 NLP 도구도 미적재 데이터나 미구현 분석 엔진을 대신하지 않는다.

## 2. 확인한 기준 상태와 이번 작업의 경계

- 기준 소스 커밋: `56c83d9`. 상세 오류: [파이프라인 검토](pipeline_repair_review_20260925.md).
- 이번 계획 작성 시 backend 컨테이너 실행 및 `/health` HTTP 200을 확인했다. 이 확인만으로 DB 전체 정상이나 모든 질의 성공을 주장하지 않는다.
- 실행 컨테이너에서 `kiwipiepy` 미설치 확인. Ollama 설치 목록은 `qwen2.5:1.5b`, `bge-m3:latest`, `gemma2:latest`; Qwen3.5 4B/9B는 미설치다.
- 이전 실제 관측 파일을 재확인했다: `live-presets-v5` 100개 응답, 관측 오류 0; COMPLETED 13 / PARTIAL 13 / NEEDS_CLARIFICATION 66 / BLOCKED 8. `contracts-v7.jsonl` 계약 검사 13/13. 단위 177 passed는 이전 실행 기록이며 이번 문서 작업에서 재실행하지 않았다.
- `intent_shadow.py` 및 `compare_web_pipeline_ollama.py`는 이미 JSON Schema를 사용한다. 새 작업의 초점은 JSON 파싱보다 **의미·출처·실행 계약 검증**이다.
- 이전 100개 비교는 lexical 후보 재생, 후속 8개는 실제 서비스 후보였다. 두 결과를 한 정확도나 모델 개선율로 합치지 않는다.
- 이번 변경은 계획 문서와 로드맵이다. 패키지 설치, 모델 다운로드, 서비스 재시작, 운영 라우팅 변경, QLoRA 학습은 이 문서 작성 단계의 완료 항목이 아니다.

## 3. 목표 구조와 연결 위치

```text
원문 + 명시된 대화/지도 문맥 + 요청 기준 시각
  → 원문 보존 / Kiwi 형태 분석 / 원문 구간 대응
  → 대상·행동·단위·부정·문맥 참조 후보
  → 슬롯 출처·유형 검증 / 필요한 산출물 계약
  → 기존 broker + registry/KG의 capability 후보
  ├─ 검증된 기존 계획 → 실제 DB/도구 → 작업별 결과·누락·근거
  └─ 고정 snapshot → Qwen shadow 평가 → 순위·제안·오류 기록
                              (실행 경로에는 반영하지 않음)
```

기존 route 이름은 호환성과 관측을 위해 남긴다. 필요한 작업 목록과 허용 capability 조합을 추가하며, 모델이 제안한 임의 도구 ID·SQL·좌표를 실행하지 않는다. 후보에 필요한 기능이 없으면 `CANDIDATE_GAP`으로 기록한다. 새로운 capability는 별도 구현·registry 등록·테스트 후 사용한다.

| 현재 연결점 | 예정 작업 | 검증 포인트 |
|---|---|---|
| `services/orchestrator/request_semantics.py` | 공통 산출물·부정·대상 계약 사용 | 문서 주제가 실행 요구를 덮지 않음 |
| `fast_path_policy.py`, `router.py`, `graph.py` | 동일 해석 결과를 공유하고 fast path 선점 방지 | REST/SSE/그래프에서 슬롯과 상태 일치 |
| `query_candidate_broker.py` | 검증 슬롯·작업 요구를 후보에 결합 | 장소와 분석의 선행·후속 관계 보존 |
| `intent_shadow.py`, `compare_web_pipeline_ollama.py` | 슬롯 근거 계약, 고정 후보 입력, 모델 어댑터와 지표 확장 | runtime 선택과 shadow 순위를 분리 |
| `traffic_execution.py`, `place_resolver.py` | 기존 기간·위치 검증에 표준 슬롯 전달 | 항만 입구 임의 좌표/과거 기간 대체 금지 |
| `data/capability_registry.yaml` 및 공간·용어 사전 | Kiwi 용어 사전과 후보 설명의 원천 | 별도 하드코딩 용어 목록의 중복 방지 |

신규 모듈명은 제안이며 구현 때 기존 계약과 중복 여부를 확인한다: `korean_query_analysis.py`(Kiwi adapter), `slot_evidence.py`(구간·출처·단위 검증), `request_obligations.py`(작업 계약). 큰 graph 파일에 질의별 조건을 계속 추가하지 않는다.

## 4. 원문 구간·슬롯 계약

### 4.1 원문과 근거 보존

- 원문은 수정하지 않고 `query_id`, `query_sha256`와 함께 보존한다. 정규화 문장은 별도 필드로 둔다.
- 구간은 원문 Python 문자열의 Unicode code point 기준 `[start, end)`로 정의한다. 한국어 자모 정규화·띄어쓰기·오타 보정을 수행하면 원문과의 대응표를 보존한다. 브라우저 UTF-16 인덱스와 직접 혼용하지 않는다.
- 각 슬롯은 `slot_type`, `raw_text`, `span`, `normalized_value`, `unit`, `source_kind`, `source_ref`, `validation_status`, `reason_codes`를 가진다.
- `source_kind`는 query/conversation/map/registry/derived/default_policy로 구분한다. query 슬롯은 `original[start:end] == raw_text` 검사, 대화/지도 슬롯은 실제 turn/feature/context ID 검사, derived 값은 입력 슬롯과 변환 버전을 추적한다.
- 기본값은 명시적 사용자 입력과 분리한다. 사용한 정책 ID와 사용자에게 공개한 기본값을 기록한다. 허용된 기존 기본 정책만 사용하며 모델이 새 기본 반경·날짜를 만들 수 없다.
- 모델 confidence는 확률이나 정확도로 표시하지 않는다. 구조 유효성·구간 일치·단위 유효성·의미 적합성·실행 가능성을 각각 기록한다.
- 원문에 있는 구간이라는 사실만으로 슬롯 유형을 인정하지 않는다. '12개월'은 시간 근거가 있지만 거리 근거는 아니다.

### 4.2 단위와 시간 정규화

거리(m/km/해리), 기간(일/주/개월/년), 달력 날짜, 버전 번호를 구분한다. 1해리=1852m처럼 결정 가능한 변환은 코드로 수행하고 원 단위를 보존한다. 음수·범위 오류·불명확한 단위는 거부/추가 확인한다. 실제 제한 값은 도구 계약에서 읽는다.

상대 시간은 요청 당시 기준 시각과 `Asia/Seoul`을 고정해 해석한다. 월·년을 고정 초로 환산하지 않는다. '최근 12개월'의 현재 월 포함 정책, '최신 적재 월'의 DB 기준, '월별'의 집계 단위는 서로 다른 필드로 둔다. 월 자료로 일 단위 요구를 완료할 수 없으면 현재 실행기의 제한을 명시한다. 모델 비교에는 동일 기준 시각과 coverage snapshot을 제공한다.

### 4.3 예시와 부정 범위

| 입력 | 필요한 해석 | 금지할 결과 |
|---|---|---|
| 부산항 최근 12개월 AIS 통항량을 구역별로 요약해줘 | 장소·기간·자료·구역별 집계; 반경 미지정 | radius=12, 임의 시작 날짜 |
| 사고 말고 침선만 1km 이내에서 찾아줘 | 사고 제외, 침선 포함, 기준 위치는 별도 확인 | 사고 검색을 필수 작업으로 추가 |
| 부산항 말고 인천항 주변 | 부산항 제외, 인천항 포함 | 첫 지명을 실행 위치로 선택 |
| 위치 없이 부근 사고를 찾아줘 | 명시 위치 없음과 상대 공간 요구; 지도/대화 근거 유무 확인 | '없'을 사건 필터로 조회 |
| 사고가 없는 구역 | 사고 부재 조건을 검증할 기간·범위·coverage 필요 | 사고 조회 자체를 제외하거나 0행만으로 안전 판정 |
| S-101 2.0 정의 | 표준 버전 | radius=2.0 |
| 지도에서 이 객체의 근거 | 실제 선택 객체 참조 | 선택 객체 없이 관련 고시로 완료 |

Kiwi의 토큰/POS는 부정 범위를 판단하는 입력이지 완성된 의미 분석기가 아니다. '없다', '제외', '말고', '아닌'의 적용 대상, 인용문·질문·이중 부정은 별도 검사한다. 모호하면 후보를 보존하고 실행 필수 슬롯만 확인한다. 전체 문장에서 특정 단어가 발견됐다는 이유로 대상을 제거하지 않는다.

## 5. Kiwi 적용 방법

1. backend와 같은 Python/OS에서 wheel 설치 가능 여부·초기화 시간·메모리·라이선스를 확인하고 버전을 고정한다. 컨테이너에만 임시 설치한 상태로 완료 처리하지 않고 의존성 및 이미지 빌드 경로를 반영한다.
2. registry의 해양 용어·별칭으로 사용자 사전을 생성한다. 사전 hash와 원천 버전을 기록한다. 용어 등록은 지명 확정이나 사실 검증이 아니다.
3. 요청마다 모델을 새로 로드하지 않는다. 프로세스 초기화·워커 공유 가능성·동시 호출 동작을 검증하고 이벤트 루프를 막지 않도록 실행 경계를 둔다.
4. 먼저 관측 모드에서 기존 슬롯과 비교한다. 원문 대비 임의 교정으로 항만명·식별자가 바뀌는 경우 채택하지 않는다.
5. Kiwi 미설치/초기화 실패 시 `KOREAN_ANALYZER_UNAVAILABLE`을 관측에 남긴다. 검증 가능한 기존 경로만 유지하고 Kiwi를 사용했다고 표시하지 않는다. 이 fallback도 같은 부정 사례 검증을 거친다.
6. 결정론 검증을 실행 경로에 반영할 때는 단위 회귀와 실제 API 대표/부정 질의를 함께 통과해야 한다. 모델 shadow 도입과 별도 변경 단위로 관리한다.

## 6. 작업별 계획과 완료 판정

요청은 `required_tasks`, `allowed_capability_sets`, `dependencies`, `required_slots`, `required_evidence`, `requested_outputs`, `forbidden_actions`로 표현한다. 각 작업은 NOT_RUN/BLOCKED/NEEDS_CLARIFICATION/EXECUTED/PARTIAL/COMPLETED 및 도구 요청 ID·결과 참조를 갖는다. EXECUTED는 호출 사실이며 산출물 완료와 구분한다.

예를 들어 침선 반경 검색은 위치 해소 → 공간 검색 → 객체/거리 제시다. 사고 원인 분석을 추가로 요구했을 때만 사고 근거 조회를 추가한다. 통항량 요청은 장소 후보의 순위와 무관하게 위치·기간·자료·집계 작업 모두를 확인한다. 문서 조회는 feature→portrayal rule→symbol 매칭의 실행 증거를 대신하지 못한다.

필수 작업이 누락되면 최종 COMPLETED를 금지한다. 의도는 적절하지만 원천 미적재인 경우 의도 실패와 실행 불가를 분리한다. 명시 위치/문맥이 없거나 모호한 경우 필요한 입력만 요청하며, 제공된 위치를 다시 묻는 것도 평가 오류다.

## 7. Qwen3.5 4B/9B shadow 실험 설계

### 7.1 동일 입력과 비교군

실제 서비스의 query/context/기준 시각/candidate ID·순서·점수·capability 설명·입출력·registry 버전·coverage를 하나의 불변 평가 snapshot으로 만든다. 모든 모델이 동일 snapshot을 사용한다. 후보 설명을 모델마다 다르게 줄이거나 lexical 재생 결과를 실제 후보로 대체하지 않는다. 입력이 제한을 넘으면 잘린 항목과 실패를 기록하고 전체 비교군에 동일 정책을 적용한다.

| 비교군 | 변경 변수 | 목적 |
|---|---|---|
| A | 현재 규칙/registry | 기준선 |
| B | A + 원문·단위·부정·Kiwi | 한국어 보강 자체 효과 |
| C | 고정 후보 + Qwen2.5 1.5B | 과거 모델을 새 계약에서 재평가 |
| D | C와 같은 입력 + Qwen3.5 4B | 모델 교체 효과 |
| E | 같은 입력 + Qwen3.5 9B, 조건부 | 추가 자원 대비 품질 |
| F | 규칙 + 모델 점수 + registry/context gate | 혼합/보정 효과 |

A/B의 후보 생성 효과와 C/D/E의 고정 후보 순위 효과를 별도 보고한다. 후보에 정답 기능이 처음부터 없는 경우 모델 오분류와 구분하고, 필요한 capability의 후보 포함률도 보고한다. F는 calibration split에서만 가중치·온도를 정하고 holdout에서 재조정하지 않는다. 온도 1을 넣은 결과를 학습된 calibration이라고 부르지 않는다.

### 7.2 모델 호출 계약과 자원 조건

- 4B부터 시작한다. model tag뿐 아니라 digest·양자화·Ollama 버전·prompt/schema hash·seed·sampling·context/output 한도·thinking 설정을 보존한다. 모델별 템플릿 차이는 adapter 버전으로 기록한다.
- JSON Schema는 유지하고 원문 슬롯 근거, 요구 작업, 후보별 충족/미충족 산출물, 판단 유보 이유를 추가한다. 모델 설명은 짧은 근거 요약이며 실제 도구 실행 증거는 별도 참조한다.
- 생각 모드 on/off를 섞어 비교하지 않는다. 개발셋에서 파싱·지연을 점검해 설정을 고정하고, 모드 비교가 필요하면 별도 실험군으로 둔다.
- GPU/VRAM·RAM·디스크·CPU offload·기존 서비스 사용량을 먼저 측정한다. 다운로드 파일 크기를 필요한 실행 VRAM으로 취급하지 않는다.
- 초기 오프라인 설정은 동시 모델 요청 1개, 질의별 총 제한 120초, 자동 재시도 0회를 제안한다. cold load와 warm inference를 분리한다. 실패를 삭제하지 않고 재시험은 새 run ID로 남긴다.
- 9B는 4B 검증 후 별도 워밍업 10문항에서 OOM/timeout이 없고, 측정 peak 이후 RAM/VRAM 각각 20% 이상 여유, API 계약 유지 및 통제된 병행 부하에서 API p95 지연 증가 10% 이하일 때 전체 평가를 진행한다. 이는 사전 제안 운영 기준이며 측정 전 성능 보장이 아니다. 미충족이면 SKIPPED_RESOURCE_LIMIT으로 기록한다.
- 먼저 API 평가와 모델 평가를 순차 실행한다. 이후 별도 bounded queue·timeout·취소·부하 격리 검증을 수행한다. 상시 shadow는 요청 응답의 필수 경로에 넣지 않는다.
- 전 실험에서 `used_for_execution=false`를 유지한다. shadow 선택으로 실제 도구를 중복 실행하거나 운영 결과를 바꾸지 않는다.

## 8. 정답셋과 지표

### 8.1 독립 정답셋

기존 웹 샘플 100개는 이미 오류 분석·수정에 사용했으므로 **개발/회귀셋**이다. 이를 독립 holdout이라고 부르지 않는다. AI 판단은 REVIEW_REQUIRED로 저장하며 human gold로 승격하지 않는다.

초기 수집 목표는 웹 100개 외 독립 200개 이상이다. 신규 항만/표현/대화·지도 문맥을 포함해 calibration 100개와 locked holdout 100개 이상을 그룹 단위로 나눈다. 이 규모는 첫 비교를 위한 계획값이며 QLoRA 학습에 충분하다는 뜻은 아니다. 학습용 데이터는 별도 수집한다.

동일 원문 변형·동일 대화·템플릿·유사 합성 사례가 split을 넘지 않도록 lineage와 중복 검사를 둔다. 형태 변형, 단위, 부정, 복합 작업, 정의/실행, 지시어, 후보 부족, 자료 미적재를 포함한다. 각 항목은 허용 작업 조합·슬롯 근거·명시 제외 대상·추가 질문 필요성·실행 허용 범위·판단 이유를 가진다.

검수자는 가능하면 모델 출력을 보기 전에 독립 작성한다. 2인 검토 및 불일치 조정을 목표로 하며 단독 검수분과 합의분을 구분한다. 사람이 제공되지 않은 상태에서도 수집 도구·계약·개발셋 회귀는 진행하되, 독립 정확도·운영 승격·QLoRA 판단은 미검증으로 남긴다.

### 8.2 주 지표의 정의

| 지표 | 계산/판정 기준 |
|---|---|
| 필요 작업 계획 충족률 | 허용된 조합 기준으로 계획이 포함한 필수 작업 수 / gold 필수 작업 수. 의존성과 입출력 호환도 검사 |
| 실제 작업 완료율 | 실제 증거로 산출물을 충족한 필수 작업 수 / gold 필수 작업 수. 계획 충족률과 별도 보고 |
| 슬롯 정확도 | 유형별 원문 span exact match/F1, 정규화 값 exact match, 전체 슬롯 동시 정답률; null/문맥 참조도 평가 |
| 무근거 슬롯률 | 원문·유효 문맥·허용 정책 근거가 없는 비어 있지 않은 슬롯 수 / 제안된 비어 있지 않은 슬롯 수 |
| 불필요한 추가 질문률 | gold상 추가 질문 없이 처리 가능한 사례에서 질문한 수 / 해당 사례 수 |
| 필요한 질문 누락률 | gold상 실행 전 확인이 필요한 사례에서 질문 없이 진행한 수 / 해당 사례 수 |
| 과잉 실행률 | 제외 대상·검증 전제 위반·불필요한 작업을 제안/시도한 사례 수 / 평가 사례 수. 모델 제안과 실제 호출을 분리 |
| 지연/실패 | 전처리·후보 조회·모델·검증·API 전체 p50/p95, cold/warm, timeout/파싱/검증 실패율 |

분모가 0이면 0%가 아니라 N/A이다. 파싱 실패·timeout은 전체 분모에서 제거하지 않고 유효 출력률 및 end-to-end 실패로 반영한다. 도구 데이터가 없어 실행 불가한 사례는 전체 완료율과 실행 가능 하위집합 완료율을 함께 보여 선택 편향을 방지한다. 의도 라벨 일치율은 보조 지표다.

결과는 동일 사례별 승/패/동률과 오류 유형, 표본 수, 그룹 단위 bootstrap 95% 구간을 함께 보고한다. 예시 몇 개의 개선이나 구조 통과율을 의미 정확도라고 부르지 않는다. registry exact hit·도구 호출 성공·모델 점수도 정확도와 분리한다.

## 10. 검증·승격·rollback

- 필수 회귀는 기존 `test_request_output_obligations.py`, `test_place_graph_integration.py`, `test_radius_stream_contract.py`, `test_traffic_period_contract.py`, `test_query_candidate_broker.py`, `test_intent_shadow.py` 및 신규 슬롯/한국어/부정 계약 테스트다.
- 실제 실행 검증에는 `check_pipeline_execution_contracts.py`, `check_geollm_web_samples.py`를 사용한다. query별 슬롯·후보·계획·도구 파라미터·결과·상태를 확인하며, 화면 클릭 검증과 API 관측은 구분한다.
- 원문 부정/제외 무시, 날짜/좌표 조작, 미등록 capability 실행, 필수 산출물 없는 COMPLETED, shadow의 운영 선택 변경은 승격 차단 오류다. 보유 회귀/holdout에서 관측 0건을 요구하되 이것을 미래 오류 0% 보장으로 표현하지 않는다.
- Kiwi/검증기는 독립 feature flag와 schema 버전으로 단계 도입한다. 운영 반영 전 정상 사례 손실·불필요한 질문 증가도 평가한다. 근거 검증에 실패한 값을 기존 경로로 몰래 통과시키지 않는다.
- 모델 실행 권한은 이 계획에서 자동 승격하지 않는다. 독립 평가·calibration·부하 검증 후 별도 결정 기록을 남긴다. 작업 충족률의 유의한 개선과 과잉 실행/슬롯/질문 지표 비악화를 확인한다. 비열등 허용폭과 실제 서비스 지연 SLO는 calibration 단계에서 정하고 holdout 개봉 전에 고정한다.
- rollback은 분석기 flag 비활성화, 이전 schema/registry/model digest 복원, API 계약 재검증으로 수행한다. DB 원천 데이터 변경을 요구하지 않도록 설계한다. shadow 중지는 실행 결과에 영향을 주지 않아야 한다.

## 11. QLoRA 판단 조건

현재 결정은 **DEFER**다. 모델 교체·prompt·구간/단위/부정 검증·후보 설명 보완 이후에도 같은 오류 유형이 서로 다른 독립 사례에서 반복되는지 확인한다. 개별 단어 암기, 데이터 미적재, 잘못된 registry, 도구 미구현은 학습으로 해결할 오류로 분류하지 않는다.

학습/검증/holdout 분리, 사람 검수 정답, 충분한 유형별 사례와 학습량 증가 실험, 모델 라이선스·GPU·양자화·adapter 호환·rollback이 모두 필요하다. 기반 모델/prompt 개선/adapter를 같은 잠긴 holdout으로 비교한다. holdout을 본 뒤 학습 데이터를 조정했다면 새 holdout이 필요하다.

학습 대상은 작업·슬롯·문맥 참조·근거 종류·판단 유보다. 실제 좌표·법령 내용·통항량을 모델 기억으로 반환하도록 학습하지 않는다. 조건 충족 여부와 근거 파일을 기록한 go/defer 결정서 없이 학습을 시작하지 않는다.

## 12. 재현 산출물과 문서 관리

- 소스 관리: schema/validator/Kiwi adapter/고정 의존성/registry 사전 생성기/프롬프트/테스트/평가 코드/검수 지침/변경 설명.
- 평가 원본: 새 `outputs/korean-intent-shadow/<run-id>/`에 manifest, cases, candidates, raw requests/responses, slots, plans, tool observations, metrics, errors를 분리한다. 기존 산출물을 덮어쓰지 않는다.
- 모델·registry·프롬프트·schema·Kiwi·사전·데이터 snapshot·하드웨어·기준 시각을 기록한다. 사용자의 원문/대화는 평가에 필요한 범위만 보존하며 API 키·DB 접속 문자열은 기록하지 않는다.
- 매 단계에서 [공통 로드맵](remaining_work_roadmap.md)에 구현 상태·실제 검증·남은 실패·다음 순서를 갱신한다. 기존 사용자 피드백 JSONL과 실행 로그는 소스 커밋에서 제외한다.

## 13. 도구 선정 근거

2026-09-25 공식 자료 확인 기준이다. 다음 기능의 존재와 GeoLLM에서의 효과는 구분한다.

- [Kiwi Python 공식 문서](https://github.com/bab2min/kiwipiepy): 사용자 사전과 형태소 토큰의 원문 위치 제공. 한국어 전처리 후보로 선정하며 단독 의도 분류기로 취급하지 않는다.
- [Ollama Structured Outputs](https://ollama.com/blog/structured-outputs): JSON Schema 출력 제약 지원. 기존 코드에 이미 적용돼 있어 의미 검증을 추가한다.
- [Qwen3.5 공식 모델 카드](https://huggingface.co/Qwen/Qwen3.5-4B), [Ollama 모델 목록](https://registry.ollama.com/library/qwen3.5): 4B/9B 비교 후보. 런타임 호환·양자화·메모리는 설치 환경에서 검증한다.
- [GLiNER2 기본 모델 카드](https://huggingface.co/fastino/gliner2-base-v1): 영어 명시 모델을 한국어 검증 없이 채택하지 않는다. 이번 우선 작업에는 포함하지 않는다.

이번 계획의 완료는 문서화의 완료다. Kiwi 적용, Qwen3.5 개선 효과, 독립 의미 정확도, 운영 승격, QLoRA 성과는 각각의 검증 후에만 완료로 기록한다.
