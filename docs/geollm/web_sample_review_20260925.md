# GeoLLM 질의창 샘플 100개 실제 서비스 평가

평가일: 2026-09-25. 평가자: Codex의 근거 기반 검토 의견이며 human gold 정확도 평가가 아니다.

**판단: 현재 샘플 전반에 대해 정확한 분석 결과를 제공한다고 볼 수 없다.** 단순 정의는 근거와 일치하는 사례가 있지만, 공간·통항 분석 대신 관련 문서만 반환하거나 실행하지 않은 요청을 COMPLETED로 표시하는 문제가 반복된다. route 명칭의 일치 여부가 아닌 필수 출력의 충족 여부로 판단했다.

## 검증 범위와 제한

- `http://localhost:8000/`의 실제 HTTP 페이지를 받아 `setupPresetPrompts()`의 샘플 **100개 전체**를 추출했다. 실행 시작 당시 페이지 사본과 SHA-256을 보존했다. 로컬 파일에 별도 질의를 만들어 대신 테스트하지 않았다.
- 웹 코드가 제출하는 `/api/v1/tasks/stream`으로 각 샘플을 실행했다. `user_id=admin`, `organization_id=test`, 정상 신규 질의로 제출했고 원본 SSE 이벤트·task ID·결과를 보존했다. 동시 요청은 최대 2개다.
- **브라우저 연결 목록이 비어 있어 클릭·렌더링·지도 이동은 검증하지 못했다.** Browser 스킬의 연결 진단 이후 사용자에게 연결을 요청했다. 이 결과를 브라우저 E2E 통과라고 표현하지 않는다.
- 현재 사용자의 지도 viewport·선택 feature를 관측할 수 없어 `spatial_context={}`로 제출했다. 지도 문맥을 임의로 만들어 넣지 않았다. 지도에 의존하는 샘플은 실제 UI와 조건이 다르며 후속 브라우저 검증이 필요하다. 명시적인 항만·대상·기간을 가진 샘플의 누락 결과는 이 제한과 별도로 확인했다.
- 30초 동안 스트림을 받지 못한 3건은 관측 timeout이다. 기존 task를 조회했을 때 모두 RECEIVED였으며 재실행하지 않았다. 이를 분석 실패·정답·완료로 집계하지 않는다. 관측 클라이언트의 연결 종료가 작업 취소/상태 잔류에 영향을 줬을 가능성도 있어 브라우저에서도 같은 문제가 발생한다고 단정하지 않는다.
- 테스트 중 운영 라우팅을 변경하지 않았다. 기존 오프라인 Ollama shadow와 다른 **현재 서비스 실행 경로**를 평가했다.

## 실행 장애의 확인된 원인

`load_catalog()`를 실제 컨테이너에서 읽기 전용으로 실행한 결과 후보 **1,985개**, unavailable source는 `projection.s101_feature_valid`였다. resolver 코드에 저장된 항만 집계 SQL을 그대로 실행하면 **QueryCanceled: statement timeout**이 재현됐다. 해당 함수의 SQL 제한은 5초다.

또한 `place_resolver.py`의 지명 해소 경로는 카탈로그에서 이름과 일치하는 후보가 있어도 `unavailable_sources`가 하나라도 있으면 결과 반환 전에 전체 해소를 차단한다. 따라서 항만 집계 장애가 독도·도서/해양지명 등 다른 원천의 후보에도 전파될 수 있다. 이 정책을 검토할 때 미확인 원천을 정상으로 위장하거나 임의 좌표로 대체해서는 안 된다. 원천별 격리, 검증된 후보만 사용, 복수 후보 충돌 처리와 provenance 보존이 필요하다.

외부 후보 확인 응답 중 geometry가 null이고 일반 OSM 설명만 있는 항목도 관측했다. 실제 지오코딩 결과인지 조회 계획인지 구분해 후속 검증해야 하며, 현재는 성공적인 위치 해소로 집계하지 않았다.

## 다음 수정·검증 우선순위

1. 항만 gazetteer 집계의 5초 timeout 원인과 원천 간 장애 전파를 수정하고 같은 지명·반경 샘플을 재검증한다.
2. 필수 결과 계약으로 완료를 판정한다. 통항 집계·지도 객체·Feature 코드·시스템 진단 결과가 없으면 관련 문서 검색만으로 COMPLETED를 반환하지 않는다.
3. 요청 행위·출력·시간·공간 슬롯을 유지하도록 법령/정의 fast path와 실행 계획을 비교한다. 샘플마다 새 키워드 분기를 덧붙이는 방식으로 해결하지 않는다.
4. 공간 적재, 문서 임베딩, live DB 동작 검증을 각각 실제 실행 도구·관측값에 연결한다.
5. 40–42번 스트림 중단과 RECEIVED 잔류를 조사한다. 브라우저 연결 후 100개 샘플의 화면 표시·지도·클릭 문맥을 검증하고 서비스 관측과 구분해 보고한다.
6. 이 결과를 요청 충족 기준의 shadow 평가에 연결한다. QLoRA로 DB 장애나 실행 계획 누락을 해결하려 하지 않는다.
