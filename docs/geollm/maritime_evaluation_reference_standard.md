# 해양 GeoLLM 정답 근거와 평가 기준

2026-09-26. 사용자 제안인 법령·고시, S-101 FC/PC/DCEG 2.0 및 해양 위키를 하나의 평가 체계로 연결한다. 이 문서와 `configs/evaluation/maritime_reference_policy.yaml`은 검수 설계 기준이다. 원천 수집·서명 검증·gold 승인 및 런타임 강제 검증까지 구현했다는 뜻은 아니다.

## 왜 위키도 필요하며 어떻게 구분하는가

위키는 편집·제공 형식이다. 기관의 책임, 문서의 적용 범위와 개정 이력이 권위를 결정한다. [IALA 공식 사전](https://www.iala.int/wiki/dictionary/index.php?page=Main+Page)도 위키로 제공된다. 공식 사전의 특정 판·항목은 해당 용어의 기준 후보가 될 수 있지만, 사전의 정의만으로 법적 의무나 모든 표시 조건을 확정할 수 없다. 이번 확인에서는 검색 색인으로 공식 사전의 존재를 확인했으며 직접 본문 요청은 403이었다. 개별 항목의 내용·현행성·라이선스는 아직 검증하지 않았다.

[IHO S-32](https://portal.iho.int/iho-ohi/S32/)는 IHO 표준과 간행물에 사용하는 수로 분야 용어의 공식 참조 사전이다. 한국어 별칭·번역은 원어 항목과 연결하고 번역 검수 여부를 따로 기록한다. 자체 번역을 공식 한국어 정의로 표시하지 않는다.

Wikipedia 등 일반 위키는 한국어·영어 동의어, 개념 관계, 초심자 표현, 질문 변형과 원문 출처 탐색에 유용하다. 일반 위키만으로 법령·인코딩·표시 규칙의 gold를 승인하지 않는다. 인용된 원문을 확인하고 revision/permalink를 고정한다. 자료별 재사용 조건도 수집 전에 확인한다.

## 주장별 정답 근거

| 평가 대상 | 우선 근거 | 추가 조건 |
|---|---|---|
| Feature·속성·관계의 정의 | S-101 FC 2.0.0 | canonical ID, 속성 타입, 판 고정 |
| 대상의 분류·인코딩 방법 | DCEG 2.0.0 | 절·표·조건과 FC 교차 검증 |
| 표시 기호와 조건 | PC 2.0.0 | 객체 속성·표시 설정·관련 문맥을 포함한 실행 결과 |
| 수로·항로표지 용어 | IHO S-32, IALA 공식 사전 | 항목·언어·개정판·번역 검수 |
| 법적 의무·고시 적용 | 공식 법령·고시 원문 | 시행일·관할·조항·개정 이력·적용 공간 |
| 실제 위치·통항·관측값 | 출처가 확인된 공간·관측 데이터 | 버전·시공간 coverage·CRS·단위·쿼리·실행 ID |
| 별칭·배경·다양한 질문 표현 | 일반 위키와 해양 참고자료 | 원문 대조 후 보조 근거로 사용 |

[IHO의 S-101 2.0.0 배포 항목](https://registry.iho.int/productspec/view.do?category=product_ID&domainS=ALL&idx=214&product_ID=S-101&statusS=5)에서 DCEG, FC 및 PC를 함께 확인할 수 있다. 최신 개발 브랜치나 초안을 2.0.0 정답에 섞지 않는다. [국가법령정보 공동활용](https://open.law.go.kr/LSO/openApi/guideList.do)의 원문과 이력을 이용하되 개별 고시의 공간 정보 적재 여부까지 따로 확인한다.

모든 분야에 하나의 출처 순위를 적용하지 않는다. 법령은 법적 적용의 기준이고 PC는 표시 규칙의 기준이다. 적용 범위가 다른 문서를 다수결로 합치지 않는다. 상충 시 두 근거와 시점·판·관할을 보존하고 판정 보류 또는 검수 조정을 한다.

## 내용의 정답과 행동의 정답

문서가 사실의 기준이어도 사용자의 의도를 자동으로 정해 주지는 않는다. 예를 들어 '부산항에서 반경 1해리 안의 침선을 찾아줘'에는 위치 해소, 1852m 정규화, 침선 Feature 연결, 공간 검색과 결과 근거가 필요하다. 부산항 후보가 복수이면 실제 문맥으로 해소하거나 확인을 요청한다. 침선과 사고가 지식그래프에서 연결되어도 사고 원인 분석을 임의로 추가하지 않는다.

'이 침선이 왜 이 기호로 표시됐어?'에는 선택 객체의 ID·속성, PC 판과 조건, 해당 표시 실행의 근거가 필요하다. 침선 정의를 인용하는 것만으로는 요청이 충족되지 않는다. '사고가 없는 구역'에는 기간·조사 범위·자료 coverage가 필요하며 조회 0건을 실제 사고 부재로 확정하지 않는다.

각 gold 사례에는 원문·실제 문맥, 필요한 작업, 허용 도구 조합, 슬롯 원문 구간/정규값, 금지 행동, 필요한 추가 질문과 다음 근거를 연결한다.

```text
source_id, edition_or_revision, locator(조항/절/Feature/규칙/항목),
retrieved_at, sha256, claim(검증할 최소 주장), applicability,
review_status, reviewer_ids, adjudication_rationale
```

hash는 동일 파일 재현을 위한 값이며 발행기관의 진위나 서명 검증을 대신하지 않는다. 초안 작성자는 AI일 수 있으나 승인되지 않은 사례는 UNREVIEWED/AI_REVIEW_REQUIRED다. 검수자가 규정·문맥과 대조한 뒤 HUMAN_VERIFIED로 승인한다. 모델이 작성한 근거 설명을 정답으로 자기 채점하지 않는다.

## 온톨로지·KG·도구와의 연결

한국어 별칭 → 공식 개념/Feature ID → 속성·관계 및 출처 → 요청 작업 → capability 입력 조건 → 실제 도구 요청 → 실행 결과와 출처의 순서로 추적한다. 모든 관계에 출처·판과 검수 상태를 유지한다. 일반 위키에서 발견한 관계는 후보로 추가하고, 공식 관계와 동일 권위로 병합하지 않는다. KG의 연관성은 후보 확장에 사용하고 도구 실행 필요성은 사용자 요구와 필수 산출물로 판정한다.

현재 구현의 슬롯 근거·semantic binding·KG seed·capability 계약에 이 참조 체계를 연결하는 것이 다음 단계다. 이번 YAML은 정책 파일이며 런타임에서 자동 로드·강제되는 registry가 아니다.

## 점수와 독립 평가

현재 평가기는 검수 gold가 있을 때 명확한 단일 intent의 accuracy/macro-F1, 허용 대안 조합을 고려한 tool-plan precision/recall/F1, raw 슬롯 종류·값 F1 및 clarification F1을 계산한다. ambiguous intent는 단일 라벨 정확도 분모와 별도로 공개한다. 실패 응답은 평가 분모에 남기며 gold 없는 의미 지표는 null이다.

추가 구현 대상은 출처 선택 F1, 최소 주장별 근거 적합도, 정규화·원문 span 슬롯 F1, 실제 작업 완결도 및 신뢰구간이다. 법적·표시·공간 오류를 평균 점수로 가리지 않고 유형별로 공개한다. 원문 계약 통과율·도구 성공률·답변 정확도는 서로 다른 지표다.

웹 100개는 개발 회귀셋이다. 독립 holdout은 새로운 해역·용어·표현·복합 작업으로 만들고 동일 조항이나 질문 템플릿의 변형이 학습/검증/holdout에 분산되지 않도록 lineage로 묶는다. 공개 위키와 표준은 모델 사전학습에 포함됐을 가능성을 배제할 수 없으므로 암기 지식 점수와 새로운 문맥에서의 작업 수행 점수를 분리한다.

다음 실행은 (1) 원천 판·개정·파일 hash 및 재사용 조건 확인, (2) 주장별 locator와 개념 ID 연결, (3) 모델 출력 없는 검수 양식에 근거와 작업 라벨 작성, (4) 독립 검수·조정, (5) 동일 후보의 규칙/Ollama/혼합 평가다. 현재 human gold가 없어 의미 정확도·F1 실측값은 없으며 QLoRA는 DEFER다.
