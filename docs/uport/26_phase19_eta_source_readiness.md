# 19단계: 반복 관측과 입항 전 이력 품질 재평가

2026-09-20 운영 `eta-history-collector`의 SQLite 볼륨을 읽어 품질을 재평가했다. `docker exec geollm_eta_history_collector python -m scripts.build_uport_eta_dataset`으로 같은 보고서를 다시 얻을 수 있다.

| 지표 | 관측값 |
|---|---:|
| 누적 고유 위치 | 702 |
| 항차 키가 완전한 항차 | 97 |
| 서로 다른 위치 레코드 갱신시각이 2개 이상인 항차 | 61 |
| `입항` 이벤트 행 | 85 |
| `jobDt`와 `ptentDt`가 같은 유효 입항 행 | 85 |
| 확인된 입항 이벤트보다 앞선 갱신시각이 하나라도 있는 항차 | 0 |
| ETA 학습 후보 항차 | 0 |

반복 수집 자체는 작동한다. 다만 `updtTm`은 공식 Swagger상 **갱신시각**이며 AIS 실제 관측시각으로 확인되지 않았다. 현재 항내 위치의 갱신시각도 결합된 `입항` 이벤트 이후여서 ETA 입력으로 사용할 수 없다. 입항 이벤트가 아직 없는 항차의 위치는 저장해 두고 이후 이벤트가 게시되면 재평가한다. **입항 전 해역의 AIS 궤적을 제공하는 별도 승인 데이터 소스가 필요하다.** 현재 `marine_geo.ocean_data.ais_tracking` 테이블은 0행이고, 기존 AIS 분석 코드가 기대하는 과거 CSV도 운영 저장소에 존재하지 않는다. 과거 CSV의 연도가 현재 항차와 다르면 같은 MMSI여도 결합해서는 안 된다.

[공공데이터포털의 운항정보 설명](https://www.data.go.kr/data/15156628/openapi.do)은 `입항` 등을 운항 프로세스 항목으로 열거하고, `입출항일시`와 `작업일시`를 별도로 제시한다. [위치정보 설명](https://www.data.go.kr/data/15156631/openapi.do)에도 원천 시각의 시간대는 명시되지 않는다. `jobDt`와 `ptentDt`의 관측상 일치는 제공기관의 실제 입항 기준 확인을 대신하지 않는다. 시간대와 이벤트 의미를 확인할 때까지 데이터셋 내보내기 게이트를 유지한다.

품질 보고서는 반복 위치 항차, 입항 이벤트 시각 일치, 입항 전 관측 항차를 각각 표시한다. 동일 시각에 서로 다른 MMSI가 섞이면 중복 시각을 정리하기 전에 항차 전체를 제외한다. 이 규칙은 선박 식별 충돌이 정상 이력으로 보이는 것을 막는다.

다음 단계는 입항 전 해역을 포함하고 항차 또는 MMSI와 관측 UTC가 명확한 AIS 공급원을 확보한 후, 공간·시간 범위를 검증해 현재 입항 이벤트와 결합하는 것이다. 그 전에는 ETA 학습 또는 성능 수치를 게시하지 않는다.
