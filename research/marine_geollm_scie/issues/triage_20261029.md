## 웹 shadow timeout 조사

`services/orchestrator/live_intent_comparison.py`의 `compare`는 metadata10초, inference180초 기본값이다. 연구 `baselines/self_reviewer.py`의40초 제한이 운영에 적용되는 것은 아니다. `ComparisonStore.submit`은 큐에 넣고 즉시 ID를 반환하며 별도 worker가 추론한다. `router.py`는 이 submit을 사용한다. 따라서 연구 timeout2건만으로 웹 질의 실행이 차단된다고 결론 낼 수 없다.

분리 probe `test_timeout_triage.py`는 실제 production compare 함수를 사용하고 transport만 주입한다. 정상 metadata 후 inference180초를 전달하는지, metadata timeout이면 generate를 호출하지 않고 FAILED/called=false와 rule ranking을 남기는지를 검사한다. 이는 제어 흐름 재현이며 실제 네트워크 지연 측정·live API 실패 증거가 아니다.

metadata 실패가 해당 shadow 비교를 중단하는 것은 확인 가능한 정책이다. 그러나 metadata를 생략하면 model digest가 없는 비교가 생기므로 자동으로 우회하는 변경을 하지 않았다. live에서 동일 현상과 사용자 영향이 재현되면 모델 식별 근거와 오류 노출 정책을 먼저 정의하고 최소 수정한다.

## 후속 수정 절차

1. 원본 run ID·source hash를 고정한다.
2. 운영 오류 후보마다 정상/부정 요청과 redacted trace로 재현한다.
3. 재현된 production bug만 별도 수정 및 테스트한다.
4. 실제 API 대표 정상·부정 검증을 새 run에 저장한다.
5. before/after는 원본 실험을 덮어쓰지 않고 연결한다.

이번에는 production 수정이 없으므로 변경 후 live 검증을 완료했다고 주장하지 않는다. 기존 pilot이 확보한 공간 검증 범위는 full web pipeline이 아니다. 구조화 상세는 `findings.json` 참조.

## 실제 분리검증 결과

- 호스트 첫 실행:27 passed/2 failed. 두 실패 모두 정상모델응답 경로에서 jsonschema 부재로 실패한 환경 문제이며, 신규 probe가 명시한 오류는 `ModuleNotFoundError: No module named 'jsonschema'`다.
- 동일 소스, docker-backend, network none, repository read-only: **29 passed, 1 warning in14.73s**. 경고는 기존 starlette multipart deprecation이다.
- 실행 중 geollm_backend에서도 jsonschema import 성공을 확인했다. 패키지 부재를 숨기기 위해 JSON schema 검증을 약화하지 않았다.
- 후속 환경 복구: 호스트 `.venv`에 누락된 jsonschema 의존성만 설치했다. 최종 metadata 확인은 jsonschema4.26.0, jsonschema-specifications2025.9.1, referencing0.37.0, rpds-py2026.6.3으로 기존 lock과 일치한다. 최초 pip resolver가 rpds-py2026.9.1을 선택하여 곧바로 lock의2026.6.3으로 맞춘 후 검증했다. pyproject/lock/운영소스/원본run 변경 없음.
- 동일 호스트 재검증: **29 passed, 1 warning in5.30s**. before27pass/2fail과 구분하여 기록한다. 이는 host 환경 복구 증거이며 모델 성능 개선이나 live API 검증으로 간주하지 않는다.
